# paged.data — full analysis

**v1.0 · 2026-10-05 · input for the gates, performance, testing and Data Merge parity work**

What `paged.data` is today, measured against the everyday fundamentals of database publishing
as InDesign Data Merge and EasyCatalog define them, plus the test, CI and performance state as
found. What ships is listed in [`status.md`](../status.md); this record is the analysis behind
the next round of work and the corrections it made to other records.

Evidence tags, used on every claim that matters:

- **[C]**: verified by reading code or by grep on 2026-10-05 (the grep is named where absence
  is claimed).
- **[M]**: measured on 2026-10-05 by running it.
- **[S]**: reported by one of the three surveys and not re-verified. Treat it as a lead.

Paths are relative to this repository unless they name another one; `B` stands for
`packages/data-bundle/src`. Code lines are read at commit `bdd3fd4` (`@paged-media/data`
`0.1.0-canary.9`).

## 1. Method

Three read-only surveys (performance hot paths; tests and CI; feature gaps against InDesign
Data Merge, EasyCatalog, the feature registry, the platform gap register and the host doors),
then a re-check of every headline claim by grep against this repository, the plugin contract
(`paged-media/plugin-sdk`, published `@paged-media/plugin-api` `0.2.39-canary.0`) and the
editor. One survey claim was wrong (§8). The plan follows the shape used for `paged.draw`,
`paged.image`, `paged.sheet` and `paged.web`: gates and pins first, a count-based measurement
harness, optimisations that lower a budget in the commit that earns them, oracle-driven
correctness (InDesign Data Merge recorded on a Mac and replayed in CI), the missing
fundamentals, and one batched engine protocol change.

## 2. Headline

1. **CI could not go red on a test.** `.github/workflows/rust.yml:43` ran nextest with
   `|| true`, `.github/workflows/vitest.yml:75` ran vitest with `|| true`, neither ran on a
   pull request, and no workflow ran `tsc`. `publish.yml` published on every push to `main`
   (`.github/workflows/publish.yml:7-8`), in parallel with CI, without running a test. [C]
2. **The published package has no query engine.** The manifest declares
   `bin/duckdb-engine.wasm` (`packages/data-bundle/manifest.json:27-32`), but no workflow ran
   `scripts/vendor-duckdb.sh`; the published `0.1.0-canary.9` tarball is 11 files with no
   DuckDB. The runtime loads DuckDB from `vendor/duckdb-wasm/dist/`, not from the governed
   file (`B/query/duckdb.ts:44`, `B/query/duckdb.ts:76`), so the host has to serve the vendored
   folder; the editor does so only from a dev-server middleware (editor
   `apps/canvas/vite.config.ts:53-66`, `apps/canvas/vite.config.ts:404`). DuckDB never ran in
   CI. [C, M for the tarball listing]
3. **Nothing survives reopen.** Sources, queries, bindings and data sets live only in the
   session; `payload()` exists in the engine, but the bundle never writes it, although the
   container parts door (`host.parts`) and plugin parts in `exportPaged` exist. [C]
4. **The preview stepper writes through stale offsets.** `previewRecord` writes a variable
   with the story offset cached when the field was placed (`B/session.ts:1355-1359`), not a
   fresh `placeholders()` read; any edit before the field in that story moves the write. [C]
5. **Refresh writes front to back from one read.** `refreshFields` reads `placeholders()`
   once (`B/session.ts:1390`) and then sends one awaited `setFieldValue` per changed field
   (`B/session.ts:1412`): a value whose length changes shifts every later field in the same
   story, and a refresh of N fields is N undo steps. It also ignores sync state, so a field
   the user overrode is rewritten (ADR 553). [C]
6. **Re-lowering duplicates.** A table (`B/lower.ts:93-112`), barcode (`B/lower.ts:509`) or
   preview step mints new content every time; nothing removes or updates the earlier frame or
   paths. [C]
7. **Errors are swallowed.** `refreshFields` returns 0 when the engine or the placeholder read
   fails (`B/session.ts:1383-1392`); `variables()` returns `[]` with a log line
   (`B/session.ts:920-935`); CSV import failures reach only the log [S]. The panel shows "this
   editor can't share it with other plugins yet" after every successful publish
   (`B/panels/dataset-panel.tsx:157-160`), although `host.dataProviders` exists. [C]
8. **Built, not reachable.** The panel defines variable, image and barcode bindings only
   (`B/panels/bindings-panel.tsx:204-237`); its only query is `SELECT * FROM <first source>`
   (`B/panels/bindings-panel.tsx:216`); a variable from "Add binding" gets an empty expression
   (`B/panels/bindings-panel.tsx:219`). Table, rule and visibility bindings are session-only.
   Record flow has no define method on the session (`B/session.ts:311-371` lists the `add*`
   methods; none is a record flow) and no writer, so the panel's "Run batch" always answers
   that no record-flow binding exists (`B/panels/dataset-panel.tsx:135-137`). There is no merge
   into a document and no live refresh. Local import is CSV and TSV only
   (`B/panels/sources-panel.tsx:100`). [C]

## 8. Records that disagree with the code

Corrected on 2026-10-05 unless marked otherwise.

- **The repository orientation file** said remote sources, record flow, rules, governed
  extract, batch generation and the provider contract are "NOT implemented at M0"; most are
  built in the engine and several in the bundle. Corrected to the reachability picture above.
- **The README** described the "M0 / T0 spine", pointed at a retired breakage log, and gave an
  end-to-end command filtered on `@paged-media/data-bundle`, a package name that does not
  exist (the package is `@paged-media/data`). Corrected.
- **The coverage gate wording** ("fails below 100% tests-per-implemented-row") described
  existence, not passing. The gate now also requires each mapped test to have run and passed
  in the nextest report.
- **`manifest.json` version** `0.0.1` against package `0.1.0-canary.9`. Aligned.
- **Feature registry rows** (claims edited, not prose): governed extract was claimed shipped
  (the kernel is; nothing reads a sidecar from a location, and the panel passes an empty one,
  `B/panels/dataset-panel.tsx:100`); the performance gates were claimed shipped, citing a
  1M-row DuckDB gate that exists nowhere. Both are now partial.
- **Platform gap register:** the caret door (C-9) is published and wired; the per-cell style
  residual (D-13) is closed; created-story addressability (D-16) is now plugin-only through
  `MutationOutcome.minted[].story`. Network consent (D-03, the page CSP), the large-artifact
  ceiling (D-07b) and the chart-data contract (D-15) stay open. The 2026-06 rolled-up table of
  this plugin's platform gaps, which still showed D-04, D-06, D-09, D-10, D-11 and D-12 open,
  is marked superseded.
- **Comments that still describe closed gaps** (being corrected with the data fixes): the
  provider door at `B/session.ts:499` and `B/panels/dataset-panel.tsx:24,157`; the caret door
  at `B/lower.ts:164-216`; a 64 MiB DuckDB ceiling at `B/query/duckdb.ts:31` and in
  `scripts/vendor-duckdb.sh`, where the manifest declares 48 MiB and `plugin-cli` allows
  100 MB for an engine artifact.
- **Survey claim corrected here:** the `mvp` DuckDB variant (40,621,595 bytes) is under the
  48 MiB (50,331,648 bytes) cap, not over it; what exceeds every cap is the three variants
  together.
